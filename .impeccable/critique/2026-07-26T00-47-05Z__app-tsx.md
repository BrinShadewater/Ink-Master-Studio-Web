## Priority Issues

### [P1] Core canvas manipulation remains pointer-dependent

Location: `components/editor/EditorCanvas.tsx`, with precise placement gated by mode in `components/editor/EditorInspector.tsx`.

Why it matters: dragging artwork and operating crop handles have no complete keyboard equivalent. Basic mode also hides the strongest numeric fallback. A keyboard-dependent user can be blocked from a core preparation task.

Fix: make the selected layer movable and resizable with keyboard commands, provide focusable crop handles or equivalent controls, and expose an accessible precise-placement fallback without requiring Advanced mode.

Suggested command: `$impeccable harden`

### [P2] Basic mode loses its guided path after import

Location: `components/editor/EditorToolbar.tsx` and `components/editor/EditorInspector.tsx`.

Why it matters: the empty state presents one clear action and a three-step workflow. After import, Basic mode exposes eight tools. At 390 pixels the toolbar labels remain readable, but the new purpose and Recommended next context is hidden. First-time and interrupted users must infer the sequence again.

Fix: keep a compact current-step and recommended-next prompt visible on mobile. Move specialist preparation tools behind Advanced or a More tools control, while preserving direct access for experienced users.

Suggested command: `$impeccable onboard`

### [P2] Mobile chrome compresses the working canvas

Location: the mobile grid in `components/editor/EditorApp.tsx`.

Why it matters: the 112-pixel project header, fixed inspector region, and bottom tool rail leave a shallow artwork workspace on short phones. The inspector scrolls correctly and targets are large enough, but visual placement receives less space than its importance warrants.

Fix: let the inspector collapse into a bottom sheet or compact summary, then allow the canvas to reclaim height. Keep the current tool and primary next action near the thumb zone.

Suggested command: `$impeccable adapt`

### [P2] Compare introduces a second page-level heading

Location: `components/editor/CompareBoard.tsx`.

Why it matters: the editor already owns the page-level `h1`. Compare should sit beneath it in the semantic hierarchy so screen-reader heading navigation reflects the visible structure.

Fix: change the Compare heading to `h2` and retain the existing section label.

Suggested command: `$impeccable harden`

### [P3] Small design-system drift remains

Location: four `11px` labels plus the Compare preview substrates and Crop guide color.

Why it matters: these do not harm the current appearance, but they make future visual maintenance less predictable and weaken the otherwise disciplined token system.

Fix: document the `11px` operational step or normalize those labels to 10px or 12px. Map the functional preview colors to named tokens or document them as deliberate exceptions.

Suggested command: `$impeccable polish`

## Persona Red Flags

### Jordan, first-time user

Jordan gets a strong empty state, then Basic mode exposes nearly the complete preparation toolbox. Trace, DPI, variant, RGB, and proof need concise outcome-focused explanations. Mobile removes the recommendation that would otherwise help Jordan choose the next tool.

### Sam, accessibility-dependent user

Sam benefits from visible focus, accessible names, live status, dialog focus management, and mobile tool labels. Canvas dragging and crop manipulation still lack complete keyboard equivalents, while the duplicate page-level heading weakens structural navigation in Compare.

### Casey, distracted mobile user

Casey receives large touch targets, no horizontal page overflow, persistent local saving, and a thumb-friendly tool rail. The fixed header and inspector reduce the canvas on short phones, and the hidden mobile recommendation makes interruption recovery harder.

### Maya, first-time print-on-demand seller

Maya sees a credible Printify target and a strong final receipt. Readiness signals are concentrated late in Product and Export, so resolution or transparency problems can still feel like late discoveries. A compact persistent readiness summary would strengthen the product-specific workflow.
